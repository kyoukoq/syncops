# SyncOps technical guide

SyncOps is a self-hosted integration reliability platform and DevOps lab. It records synthetic CRM, ERP and TMS deliveries, makes retries and failures visible, and gives authorized operators an audited path to recovery. This guide follows the implementation and links the checks that exercised each layer. See the [current acceptance status](../PROJECT_STATUS.md) for the environments and revisions covered by those checks.

## Follow an integration event

1. The React console calls the FastAPI API through relative paths in [the browser client](../frontend/src/api.ts). Vite proxies development requests to the loopback API. NGINX does the same in Compose and Kubernetes. Integration configuration, submission, timeline, recovery and auditing use the same API that the smoke tests call. [API contract](api-contract.md) · [Application shell](../frontend/src/App.tsx) · [NGINX configuration](../deploy/nginx.conf)
2. The API authenticates the request and validates its schema and the target integration. Only `crm`, `erp` and `tms` simulator adapters are selectable. Their destination origin comes from trusted deployment settings. Webhook ingestion needs the configured webhook secret. The API commits the new SQL event and intake audit before acknowledging it. [API routes](../backend/syncops/api.py) · [Intake and replay](../backend/syncops/events.py) · [Simulator trust boundary](adr/0002-simulator-trust-boundary.md)
3. A worker claims due work in the database. It records the attempt and a time-limited lease atomically, then calls the simulator over HTTP. The simulator records its synthetic effect using the event ID. The worker records the response, next attempt time or final state through a guarded update. [Worker](../backend/syncops/worker.py) · [Simulator](../backend/syncops/mock.py)
4. The browser reads persisted state and presents events, attempts and recovery history. The internal metrics endpoint reports durable states and worker health. Worker logs carry event and correlation IDs for a cross-check in Loki. [Event views](../frontend/src/Events.tsx) · [Overview](../frontend/src/Overview.tsx) · [Correlation runbook](runbooks/trace-worker-incident.md)

## Persistence and delivery guarantees

| Concept | SyncOps implementation and trade-off |
| --- | --- |
| SQL database and persistent job queue | SQLAlchemy uses the same schema through SQLite on native Windows and PostgreSQL in the container and Kubernetes profiles. Integrations, events, delivery attempts, mock effects, sessions, worker heartbeats and audit rows are durable records. Event rows carry queue state, retry timestamps, attempt counters and lease ownership. Keeping intake and queue in one transaction avoids a database-to-broker handoff. The SQL store is an availability dependency and queue throughput shares capacity with application queries. [Models](../backend/syncops/models.py) · [Database configuration](../backend/syncops/database.py) |
| Lease and expiration | A worker reads an eligible event, then claims it only if its revision still matches. This compare-and-update prevents competing workers from taking the same revision. The claim records an attempt and a lease token and sets the lease to five times the event timeout plus five seconds. An expired-lease recovery adds an attempt record while keeping the existing retry budget. A replacement worker can reclaim an expired lease and mark the abandoned attempt interrupted. A stale owner loses its ability to complete the event because the final write checks both token and expiry. The recovery has to wait for the lease window. [Claim and finish](../backend/syncops/worker.py) |
| At-least-once delivery | An HTTP effect can commit just before a worker stops or loses its response. The worker retries when it cannot confirm completion, so the destination can receive the same event again. The mock implements a stable effect key using the event ID. A real downstream system would need equivalent idempotency. [Effect deduplication](../backend/syncops/mock.py) |
| Intake idempotency | A caller can supply an idempotency key scoped to one integration. Matching canonical request content returns the existing event. Different content for the same key returns HTTP 409. The SQL uniqueness rule covers concurrent submissions. The delivery effect key is a separate control for the downstream failure window. [Intake implementation](../backend/syncops/events.py) |
| Backoff and Retry-After | Transport timeouts and HTTP 408, 429, 500, 502, 503 and 504 are eligible for retry within the event budget. The worker uses exponential backoff with jitter and a 300-second cap for that component. A longer valid Retry-After, including an HTTP date, sets the actual minimum delay. HTTP 422 goes directly to dead letter. [Backoff implementation](../backend/syncops/worker.py) |
| Dead Letter Queue and replay | The DLQ is a view of persisted terminal events. An operator or admin can replay after resolving the cause. The replay resets the charged retry budget, keeps the event and correlation IDs and preserves existing attempts. The action is audited. Replay rejects an event outside the DLQ or a disabled integration. A synthetic failure profile can be cleared explicitly in the lab. [Replay contract](api-contract.md) · [Recovery runbook](runbooks/recovery.md) |

The [native Windows acceptance](verification.md) exercised HTTP 503 recovery, HTTP 429 Retry-After, HTTP 422 dead letter, RBAC, idempotency and expired leases against an isolated SQLite profile. The [hosted PostgreSQL drill](https://github.com/kyoukoq/syncops/actions/runs/45511422619) exercised concurrent workers and a worker crash after the mock effect committed. The replacement produced one stable mock effect for that event.

## Identity, access and audit

Authentication establishes who can use the console. [The auth implementation](../backend/syncops/auth.py) stores password hashes and session records in SQL. The API issues an eight-hour bearer token and stores its hash. The browser holds the token in memory and sends it in the Authorization header. The API checks expiry and revokes the database session on sign-out. Viewers can read operational state with restricted details. Operators can run simulations and replay. Administrators can manage integrations and inspect the full audit log. Writes enforce these permissions in the API. Audit rows capture lifecycle actions and actors. They live in the same database failure domain.

The [hosted Chromium suite](https://github.com/kyoukoq/syncops/actions/runs/45513587704) checked sign-in, role restrictions, navigation, recovery and audit. The lab uses local accounts, loopback clients, scoped simulator secrets and deployment-managed connection details. Protect configuration files and database copies, including backups. Public or shared infrastructure would require additional identity, transport and audit controls. [Verification matrix](verification.md) · [API boundary](api-contract.md)

## Deployment profiles

| Technology | Role, operation and assurance |
| --- | --- |
| Native Windows | [Start-SyncOps.ps1](../scripts/Start-SyncOps.ps1) launches the console, API, worker and simulator with local SQLite and loopback ports. It is the lightweight way to explore the application. Keep the ignored data directory and the initialization credentials together. [Native acceptance](verification.md) |
| WSL2 and Linux | WSL2 runs a Linux kernel and filesystem on the workstation. A dedicated checkout inside that filesystem keeps Linux builds and data independent of the Windows SQLite profile. Use the verified Docker context for this checkout and reach only published loopback endpoints from Windows. WSL and Windows share one physical failure domain. [Windows host runbook](runbooks/windows-container-host.md) · [Current local gates](../PROJECT_STATUS.md) |
| Images and containers | An image packages application code and dependencies. A container runs it with a filesystem, process and network boundary. The back-end image supplies the API, worker, migration and mock commands. The frontend image serves the compiled React app with NGINX. The two images use non-root processes. Runtime data lives in a database volume. [Backend Dockerfile](../deploy/backend.Dockerfile) · [Frontend Dockerfile](../deploy/frontend.Dockerfile) · [Container checks](supply-chain.md) |
| Docker Compose and networking | Compose starts the database, migration job, API, worker, mock and web with health-based dependencies. The web publishes the loopback endpoint and proxies API calls on the internal network. PostgreSQL and mock stay behind the Compose network. The named PostgreSQL volume survives container replacement and standard shutdown. Dropping a volume deletes its contents. [Compose definition](../compose.yaml) · [Hosted Compose regression](https://github.com/kyoukoq/syncops/actions/runs/45511484017) |
| Kubernetes and kind | kind runs Kubernetes nodes in containers for an isolated lab. Pods run the processes. Deployments replace unhealthy or lost pods and manage replicas and rolling application revisions. ClusterIP Services give the web, API, mock and database stable private addresses. Staging and Production Lab use separate namespaces, credentials and PVCs. Cluster-IP access and port forwarding keep interfaces local by default. [Deployment guide](../deploy/kubernetes/README.md) · [Hosted kind acceptance](https://github.com/kyoukoq/syncops/actions/runs/45512478105) |
| Helm and storage | [The chart](../charts/syncops) combines shared templates with environment values. It renders workload resources, requests and limits, probes, ConfigMaps, Secret references, an optional ingress and network policies. Each PostgreSQL StatefulSet uses its own PVC for pod replacement. A node-local volume and namespace-scoped credentials provide lab separation. NetworkPolicy enforcement depends on the cluster networking implementation. The namespaces share the physical host and kernel. |
| Rolling updates and rollback | Readiness controls when new API and web pods receive traffic. Liveness can trigger restarts. Helm can roll back a failed upgrade; in an Argo-managed environment, revert the desired Git revision and let it reconcile. An application image rollback leaves durable data and migrations in place. Plan any schema or data recovery separately. [Hosted upgrade failure and rollback](https://github.com/kyoukoq/syncops/actions/runs/45512478105) |

## CI, image publishing and GitOps

GitHub Actions runs Python, dependency, frontend and Compose regression checks. Separate workflows exercise security, Kubernetes, GitOps, metrics, logs and PostgreSQL recovery. A pull request is the review boundary for the change and its CI results. The [core workflow](../.github/workflows/ci.yml) builds the Compose application and exercises it over the web proxy. See the [actual engineering workflow](engineering-workflow.md) for branch, review and integration practices.

The [container assurance workflow](../.github/workflows/supply-chain.yml) validates both images before publishing eligible candidates or release tags to GitHub Container Registry (GHCR). An image tag is a useful label and the content digest identifies the exact image. Deploy by digest and verify its provenance and SBOM attestations. The [hosted publication run](https://github.com/kyoukoq/syncops/actions/runs/45512578781) published candidates and verified both attestations. GitOps acceptance used a separate local-registry fixture in hosted kind.

GitOps keeps desired environment revisions in Git. The declarative [Argo CD applications](../deploy/gitops/apps.yaml) track separate staging and production-lab revisions and reconcile live drift. The [release verifier](../deploy/gitops/release.py) checks the exact revision, health and digest-pinned workload rollout. The [promotion drill](../deploy/gitops/verify-argocd.sh) checks that the promoted tree matches healthy staging. It preserves the review boundary when promoting to Production Lab. A failed revision returns to a healthy desired state through a reviewed Git revert, followed by sync, health and delivery checks. The [hosted GitOps drill](https://github.com/kyoukoq/syncops/actions/runs/45513353704) observed automatic drift correction, rejected an unavailable-image revision and recovered both environments. Avoid treating a green diff or a healthy pod as proof of backend delivery. [GitOps lab instructions](../deploy/gitops/README.md)

## Observability and incident response

| Tool or measure | How SyncOps uses it |
| --- | --- |
| Prometheus | Scrapes the API's internal metrics at a 15-second interval in the Compose overlay. Inspect event status, recorded attempts and worker heartbeat with the same incident timeline. Prometheus retains a bounded local history. [Scrape and alert configuration](../deploy/observability/prometheus) |
| Grafana | The provisioned Delivery Overview visualizes real metrics. The worker incident dashboard queries Loki by a correlation ID copied from the application. Keep the Grafana credential distinct from application credentials. [Provisioned dashboards](../deploy/observability/grafana) · [Worker incident dashboard](../deploy/logs/worker-incidents.json) |
| Grafana Alloy and Loki | The worker logs structured attempts to stdout. The logging overlay uses Docker syslog to Alloy, parses production fields and writes them to Loki. The trace run demonstrated retry and success for one real event with the same ID. UDP logs are best-effort and Loki retention is bounded. Use SQL attempts and audit to confirm authoritative state. [Collector configuration](../deploy/logs/worker.alloy) · [Hosted correlation check](https://github.com/kyoukoq/syncops/actions/runs/45511230280) |
| Alertmanager | Prometheus evaluates scrape failure, stale worker heartbeat and persistent dead letters. Alertmanager groups active alerts in its local UI. To demonstrate firing and resolution, stop and restore only the worker in a disposable monitoring stack. A deliberately brief HTTP 503 can recover within the alert windows. [Alert rules and drill](runbooks/observability.md) · [Hosted alert evidence](https://github.com/kyoukoq/syncops/actions/runs/45507954694) |
| SLI and SLO | The service-level indicator is the fraction of eligible accepted events that complete within 30 seconds. The lab objective is 99% during a controlled sample of valid deliveries. Record sample size, duration and late or failed events. Keep intentional outages and invalid inputs in separately labeled drills. Track p95 queue wait and p95 time to terminal state in the reliability report. [Lab objectives](runbooks/observability.md#lab-reliability-objectives) |

Start an investigation by confirming the integration, event status, attempt timestamps and correlation ID in the console. Search that ID in Grafana, then compare heartbeat, scrape status and the attempt series around the failure. After the next successful attempt or authorized replay, check the event and the audit trail. If an alert fired, wait for Prometheus to evaluate the recovery and check its resolved state. [Incident walkthrough](runbooks/trace-worker-incident.md) · [Postmortem template](runbooks/postmortem-template.md)

## Disaster recovery

Recovery restores a known persistent state and verifies service through a new delivery. The SQLite snapshot tool takes a consistent snapshot and restores to a new path. The PostgreSQL exercise backs up the database, restores into an isolated database, compares row fingerprints and verifies API readiness and a fresh event. Keep the original database and its credentials intact when practicing. [Native recovery](runbooks/recovery.md) · [PostgreSQL reliability lab](../ops/postgres_reliability/README.md)

Recovery time objective (RTO) is the acceptable time to recover service. Recovery point objective (RPO) is the acceptable data loss between the last usable backup and the failure. The hosted PostgreSQL exercise measured restore time, the effect of an acknowledged post-backup write, queue wait and time to terminal state. See the observed results and environments in [verification](verification.md) and the [hosted PostgreSQL exercise](https://github.com/kyoukoq/syncops/actions/runs/45511422619). Backup frequency, off-host durability and workload sizing still determine achievable recovery on another deployment.

## Engineering ownership and review

The Product Owner defines the outcome, approves privileged workstation actions, reviews residual risk and decides whether the evidence supports release. The lead engineering agent coordinates implementation and integration. SyncOps registers native Codex architecture, backend, frontend, platform, QA, security and documentation roles. A native agent runs its own assigned task and reports the checks it performed. Separate implementation and independent acceptance where the work calls for it. [Agent configurations](../.codex/agents) · [Engineering assignments and workflow](engineering-workflow.md)

Git worktrees give parallel agents separate checkouts and branches over the same repository history. File ownership avoids overlapping edits. The lead reviews verified changes, brings them together and reruns relevant gates on the integrated revision. A role registration only establishes the available configuration. Recorded assignments and actual outputs show which roles ran. Use the [portfolio guide](portfolio-presentation.md) to present those distinctions and the tested limits.
